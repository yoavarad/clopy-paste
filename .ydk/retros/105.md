### Patterns
- Split into two sequential tasks: the server limit first (107), then the page behaviour (108, depends on 107). The server stayed the only authority on limits; API, Kafka record contract, store (100/user) and the 16384-byte body cap were untouched.
- The old browser `maxlength` silently truncated pasted text and counted UTF-16 units. The fix counts code points via `Array.from` and never splits a code point.
- Keeping the page a single document drove a design choice: `split.js` is go:embed'ed and inlined into main.html by the index handler (`{{SPLIT_JS}}`) instead of adding a route (ADR-019).
- Chunks are POSTed one at a time, each after the previous 202, relying on same user key -> same partition for order. On failure the page stops, restores unsent text and reports `sent k/N`.
- This was the first JS unit test in the repo, so test.sh gained a node requirement and `node --test web/split.test.js` runs in `make test`.
- The task 108 build needed one review round with fixes before tests were green.

### Rule suggestions
- Count text length in code points, never UTF-16 units or bytes, on both client and server.
- When a limit changes, update specs, component yamls and boundary tests in the same task.
- A new toolchain dependency in test.sh (node) must be confirmed available in CI before merge.

### Summary
Epic 105 lowered the text limit to 256 code points and let the page split longer text into
up to 10 ordered, numbered messages, with the server unchanged in contract and still
rejecting anything over 256.

## Follow-ups
- Ordering across chunks relies on partition affinity; no e2e case in this epic asserts multi-chunk order against a real broker.
- A chunk failure mid-sequence leaves earlier chunks already delivered (the page reports k/N); there is no rollback.
